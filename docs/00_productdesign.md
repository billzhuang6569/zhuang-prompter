# 在线拍摄提词房间产品设计 v0.1

**状态**: Draft  
**更新时间**: 2026-05-27  
**产品定位**: 面向录播拍摄现场的多人同步网页提词器  
**核心约束**: 只做两个视图：控制端、播放端

---

## 1. 产品一句话

一个不需要安装 App 的在线提词房间。控制者负责文稿、版本、样式、播放策略和现场调度；播放者负责把最终提词内容稳定显示在屏幕上，并可在本地根据手动滚动或语音识别自主推进，再把当前位置同步回控制端。

这个产品不是普通的“网页提词器”，而是：

**拍摄现场用的双端协同提词系统。**

它要解决的不是“一个人把稿子滚起来”，而是“一个拍摄团队在真实现场中，稳定地让嘉宾看到正确的、可控的、可回退的提词内容”。

---

## 2. 核心问题

真实拍摄现场里，提词器最容易失败的地方不是字号不够多，而是现场节奏不可控：

1. 嘉宾语速变化，固定速度滚动不适合。
2. 导演或编导经常在录播 take 之间改稿，需要保留旧版本、对比、回退。
3. 多屏幕、多设备、远程加入时，网络延迟让“控制端绝对遥控播放端”变得不可靠。
4. 中文、英文、日文、韩文的断行和标点规则不同，文稿显示会直接影响嘉宾阅读。
5. 舞台提示、重录点、跳段点、说话人标签等内容既要给现场使用，又不能干扰口播文本。

因此，产品设计必须承认一个事实：

**控制端不能被设计成绝对遥控器。播放端也不能是纯显示屏。**

更合理的模型是：

**控制端推送文稿、配置、播放意图和版本；播放端在本地执行滚动、语音跟随和显示，并持续回传当前位置与状态。**

---

## 3. 目标用户与场景

### 3.1 主要用户

**控制者**

通常是导演、编导、助理、现场提词员。  
他们关心的是：能不能快速改稿、控制节奏、跳段、回退、确认每个屏幕是否正常。

**播放者**

通常是嘉宾面前的提词屏、iPad、扩展屏、投屏设备或远程提词设备。  
它关心的是：画面是否干净、文字是否稳定、滚动是否符合嘉宾节奏、断线后是否还能继续。

### 3.2 典型场景

**本地扩展屏模式**

同一台电脑打开两个浏览器窗口，加入同一个房间：

- 主屏幕选择控制端。
- 扩展屏选择播放端。
- 播放端开启全屏和镜像。
- 控制者在主屏幕改稿、调样式、拖动预览、播放暂停。
- 播放端本地执行滚动，减少画面抖动和同步误差。

**远程多端模式**

不同地点的设备输入房间号加入：

- 控制端统一推送文稿、版本和显示配置。
- 播放端本地执行滚动。
- 播放端把当前位置、语音识别进度、连接状态同步回控制端。
- 控制端看到所有播放端是否在线、当前在哪一段、是否偏离主进度。

## 4. 产品原则

### 4.1 双视图，不做观察视图

MVP 只有两个视图：

1. 控制端
2. 播放端

任何人进入房间后，只能选择这两种身份之一，并且可以切换身份。

### 4.2 播放端是智能端，不是哑屏幕

播放端必须具备本地执行能力：

- 本地滚动
- 本地速度计算
- 本地手动滚动
- 本地语音识别或接收语音识别结果
- 本地渲染样式
- 本地断线保持最后状态

控制端推送的是“状态和意图”，不是每一帧画面。

### 4.3 双端都有控制权

播放端具备本地控制能力，但这不代表控制端失去控制权。

MVP 的正确模型是：

**控制端和播放端都可以控制滚动、速度、暂停和位置；区别只在于控制端发出的指令在远程场景下可能存在网络延迟。**

因此：

- 控制端仍然可以控制播放端的滚动位置。
- 控制端仍然可以调整播放端速度。
- 控制端仍然可以暂停、恢复、跳转 marker。
- 播放端也可以本地手动滚动和调整速度。
- 任意一端产生有效控制后，都要把最新状态同步到房间。
- 控制端看到的应该是播放端回传后的真实状态，而不是只看到自己发出的理想状态。

### 4.4 房间状态双向同步

任意一端改变关键状态，都应该同步给另一端。

例如：

- 控制端改字号，播放端更新显示。
- 控制端切换文稿版本，播放端切换到对应版本。
- 控制端调整播放端速度，播放端按新速度本地执行。
- 控制端拖动或跳转位置，播放端收到后跳到对应位置。
- 播放端手动滚动到下一段，控制端预览位置同步更新。
- 播放端根据语音自动推进，控制端看到当前识别文本和当前位置。

### 4.5 现场优先于完美同步

远程模式下，不追求控制端鼠标滚动和播放端像素级同步。  
产品目标是现场可用，而不是视觉上“远程完全跟手”。

因此同步优先级是：

1. 文稿版本一致。
2. 播放端显示稳定。
3. 当前位置大体准确。
4. 控制端能看见播放端真实状态。
5. 鼠标滚动这种高频操作只在本地扩展屏模式中追求跟手。

### 4.6 录播优先，不做直播式安全编辑区

本产品主要面向录播拍摄，不是新闻直播、演播室直播或大会直播提词。

因此，MVP 不引入复杂的 Safe Edit Horizon。现实使用里，控制者通常会在一遍录制前、两遍 take 之间、暂停后或重录前改稿，而不是在嘉宾正在念当前句子时热修改当前可见内容。

产品应支持：

- 拍摄前快速改稿。
- take 之间快速改稿。
- 改稿前后手动保存版本。
- 改稿后同步到播放端。
- 必要时回退到旧版本。

产品暂不追求：

- 主持人正在念当前可见行时无感热更新。
- 当前可见区域的复杂编辑队列。
- 多人同时协同改稿合并。

## 5. 房间模型

一个房间包含以下核心对象：

### 5.1 Room 房间

房间是一次拍摄提词任务的实时协作空间。

包含：

- 房间号
- 当前文稿
- 当前文稿版本
- 当前播放状态
- 当前显示配置
- 当前控制模式
- 已加入设备列表

### 5.2 Script 文稿

文稿的用户感知格式就是 Markdown。用户粘贴进来的是 Markdown，编辑的是 Markdown，导出的也是 Markdown。

系统内部可以从 Markdown 临时解析出渲染树、口播文本、marker 索引和滚动锚点，但这些都是运行时派生结果，不应该变成用户必须理解或维护的另一套格式。

文稿包含：

- 普通口播文本
- 加粗、斜体、下划线、颜色
- 说话人标签
- Stage Cue 舞台提示
- Cue Marker 场记标记
- 段落结构
- 版本历史

设计原则：

- Markdown 是文稿源格式。
- Stage Cue 和 Cue Marker 也是 Markdown 扩展语法的一部分。
- 版本快照保存 Markdown 内容和少量元数据。
- 播放端渲染前，把 Markdown 解析为可显示内容、口播文本和控制点索引。
- 滚动锚点优先使用 marker、标题、段落序号、文本片段指纹和渲染行位置组合生成。
- 不在 Markdown 里强行塞用户看不懂的隐藏 ID。

### 5.3 Playback State 播放状态

播放状态不是单一的滚动位置，而是一组可同步状态：

- 当前文稿版本 ID
- 当前段落 / marker / 字符位置
- 当前滚动像素位置
- 播放 / 暂停
- 滚动速度
- 当前控制模式
- 当前语音识别结果
- 最后更新时间
- 状态来源端：控制端或播放端

### 5.4 Display Config 显示配置

显示配置由控制端统一设置，播放端本地渲染。

包含：

- 字号
- 行高
- 字重
- 字体
- 文字颜色
- 背景颜色
- 边距
- 安全区
- 镜像
- 横屏 / 竖屏适配
- Stage Cue 显示方式
- Marker 显示方式

## 6. 两个视图

## 6.1 控制端

控制端是现场导播台，不只是遥控器。

### 核心区域

**文稿编辑区**

- 编辑 Markdown 文稿。
- 支持富文本快捷操作。
- 支持插入 Stage Cue。
- 支持插入 Cue Marker。
- 支持说话人标签。
- 支持手动保存版本。
- 支持版本对比和回退。

**预览与滚动控制区**

- 显示和播放端接近的提词预览。
- 鼠标悬停或点击后，可直接滚动预览。
- 本地扩展屏模式下，预览滚动可作为主要控制方式。
- 远程模式下，预览显示播放端回传的真实位置，不承诺像素级跟手。

**播放控制区**

- 播放 / 暂停
- 回到开头
- 跳到上一段 / 下一段
- 跳到 marker
- 速度调节
- 手动位置调整
- 切换控制模式

**显示配置区**

- 字号
- 行高
- 边距
- 颜色
- 镜像
- 安全区
- Stage Cue 和 Marker 显示开关

**设备状态区**

- 已加入播放端列表
- 每台播放端当前状态
- 在线 / 断线
- 当前文稿版本
- 当前进度
- 当前控制模式
- 延迟和最后同步时间

---

## 6.2 播放端

播放端是最终给嘉宾看的屏幕，也是本地执行滚动的智能端。

### 核心能力

- 全屏显示提词。
- 支持镜像显示。
- 支持本地滚动。
- 支持本地手动滚动。
- 支持根据语音识别自动推进。
- 支持接收控制端推送的文稿和配置。
- 支持把真实当前位置同步回控制端。
- 断线时保持当前画面，不突然清空。

### 播放端默认 UI

播放端进入正式播放后，默认不显示任何控制元素，只显示：

- 口播文本
- 舞台提示
- 场记标记

必要时可通过隐藏手势或键盘快捷键唤出简易控制：

- 暂停
- 手动滚动
- 重新同步
- 退出全屏
- 开启 / 关闭语音跟随

## 7. 控制模式

MVP 至少支持三种控制模式。

### 7.1 固定速度模式

控制端设置速度，播放端本地按该速度滚动。

适合：

- 口播节奏稳定
- 演讲稿
- 开场白
- 录制较标准的视频

同步方式：

- 控制端发送播放状态、速度和开始时间。
- 播放端本地计算滚动位置。
- 播放端定期回传真实位置。

### 7.2 手动跟随模式

控制者或播放端操作者根据嘉宾节奏手动滚动。

适合：

- 嘉宾不想被固定速度带着走
- 访谈式口播
- 现场反复停顿和改词

本地扩展屏模式：

- 控制者把鼠标放在控制端预览区滚动。
- 播放端跟随控制端状态。
- 因为同机同网络，体验可以接近实时。

远程模式：

- 不把控制端滚轮作为绝对实时遥控。
- 控制端仍然可以发送滚动、速度、暂停和跳转指令。
- 播放端收到控制端指令后，在本地执行对应动作。
- 因为网络延迟存在，控制端不承诺远程滚轮操作 100% 跟手。
- 播放端可以本地手动滚动。
- 播放端滚动后把当前位置同步给控制端。
- 控制端显示播放端真实位置。

### 7.3 语音跟随模式

系统根据嘉宾声音实时转写，并用转写结果匹配文稿位置，自动推进提词。

适合：

- 嘉宾想按自己的节奏说
- 现场不希望提词员一直手动控制
- 长稿件录制
- 多次 retake

设计原则：

- 语音识别不是为了产出最终字幕，而是为了判断“嘉宾说到哪里了”。
- 识别结果需要和当前文稿进行模糊匹配。
- 系统应优先稳定推进，不要因为识别错一个词就大幅跳动。
- 播放端应支持本地语音源，因为播放端往往离嘉宾更近。

MVP 中，一个房间同时只允许一个激活语音源：

- 可以是控制端麦克风。
- 可以是某个播放端麦克风。
- 当前语音源会把实时转写和匹配位置同步到房间。

## 8. 同步逻辑

### 8.1 核心判断

不要同步每一帧滚动画面。  
同步的是状态、配置、版本和关键位置。

### 8.2 Scroll Clock 滚动时钟

Scroll Clock 是同步滚动的核心机制。

它的作用是让控制端和播放端沟通“应该如何滚动”，而不是让控制端不断发送每一帧的位置。

一次滚动时钟可以包含：

- 当前文稿版本
- 起始锚点
- 起始偏移
- 播放 / 暂停状态
- 滚动速度
- 发出指令的时间
- 指令来源端

播放端收到 Scroll Clock 后，在本地计算当前位置并执行滚动。控制端再次改速度、暂停、跳转或手动拖动时，再发出新的 Scroll Clock。播放端会持续回传真实位置，作为房间里的当前事实。

### 8.3 控制端下发

控制端可以下发：

- 当前文稿版本
- 显示配置
- 播放 / 暂停
- 起始位置
- 滚动速度
- 手动滚动指令
- 位置跳转指令
- 控制模式
- 跳转到某个 marker
- 切换语音源
- 新的 Scroll Clock

### 8.4 播放端回传

播放端必须回传：

- 当前文稿版本
- 当前滚动位置
- 当前段落 / marker
- 播放 / 暂停状态
- 当前速度
- 当前语音识别文本
- 当前匹配置信度
- 设备在线状态

### 8.5 冲突处理

MVP 采用简单清晰的冲突规则：

1. 文稿内容以控制端为主。
2. 显示配置以控制端为主。
3. 播放位置以当前控制模式决定来源。
4. 固定速度模式下，控制端是位置主来源。
5. 手动跟随模式下，控制端和播放端都可以发起有效滚动。
6. 语音跟随模式下，激活语音源所在设备是位置主来源。
7. 当两端都在控制时，最后被房间确认并由播放端回传的状态是当前事实。
8. 当播放端回传的位置与控制端预期差异过大时，控制端提示“播放端已偏离”，而不是强行拉回。

## 9. 稿件版本管理

录播现场改稿是 MVP 核心需求，不是后续增强。

### 9.1 产品目标

让控制者敢在拍摄前、take 之间和暂停后改稿，因为任何改动都可以保存、对比、回退。

### 9.2 MVP 版本模型

采用类似 Git 的概念，但不要把完整 Git 暴露给普通用户。

核心概念：

- 当前草稿 Working Draft
- 手动保存版本 Snapshot
- 版本说明 Message
- 版本对比 Diff
- 回退 Restore

### 9.3 必须支持的操作

**保存版本**

控制者点击“保存版本”，输入可选说明，例如：

- 嘉宾现场改开场
- 删除第三段
- 加强结尾 CTA
- 第二遍拍摄版本

系统保存：

- Markdown 文稿内容
- 显示配置
- marker 结构
- 保存人
- 保存时间
- 版本说明

**版本列表**

显示：

- 版本号
- 保存时间
- 版本说明
- 与当前草稿差异摘要

**版本对比**

至少支持：

- 新增内容
- 删除内容
- 修改内容
- marker 变化
- stage cue 变化

**回退版本**

回退不直接覆盖历史，而是把旧版本恢复为新的当前草稿。  
这样可以保留完整现场修改链路。

### 9.4 MVP 不做

- 不做多人同时编辑合并。
- 不做复杂分支。
- 不做命令行式 Git 概念。
- 不做权限审批。
- 不做直播级 Safe Edit Horizon。

## 10. 文稿编辑与 Markdown 扩展

### 10.1 编辑器目标

文稿编辑不是附属功能，而是提词器体验的核心。  
编辑器必须让控制者能在录播现场快速改稿，并且让播放端稳定、清晰、符合语言阅读习惯。

### 10.1.1 Markdown-first 原则

编辑器必须让用户感觉自己就在写 Markdown。

产品要求：

- 支持直接粘贴 Markdown。
- 支持导出 Markdown。
- 支持 Markdown 源码视图。
- 支持常用 Markdown 快捷输入。
- Stage Cue 和 Cue Marker 使用明确的 Markdown 扩展语法。
- 富文本按钮只是帮助用户更快生成 Markdown，不应制造另一套不可见格式。

只基于 Markdown 做滚动锚点是可行的，但不能只依赖字符 offset。更稳的方式是：以 Markdown 为源文本，解析后生成运行时锚点索引。锚点可以来自 marker、标题、段落顺序、文本片段指纹和渲染行位置。这样既保持 Markdown 易用性，也能支持跳转、语音匹配和滚动同步。

### 10.2 多语言断行

必须重视中文、日文、韩文和英文的断行差异。

设计要求：

- 中文、日文、韩文允许按字符边界断行。
- 英文优先按单词和空格断行。
- 避免错误标点出现在行首或行尾。
- 超长英文、URL 或特殊字符串应能安全换行。
- 编辑区和播放区尽量保持稳定排版，减少改字后整屏跳动。
- 东亚字形显示要保持清晰，避免字体 fallback 导致宽度突然变化。

### 10.2.1 LLM 排版体检与术语修复

CJK-English 排版要做到完美很难，MVP 不强行把它做成完整排版引擎。

更适合的产品路径是：

1. 系统提供基础排版规则，处理常见中英文断行、标点和超长字符串问题。
2. 用户可以点击“排版体检”。
3. LLM 根据内置术语库和排版规则扫描整篇文稿。
4. 系统给出可审核的修改建议，而不是静默改稿。
5. 用户确认后，再把建议应用到 Markdown 文稿。

排版体检可以处理：

- 固定英文词组保护，例如 `Final Cut Pro`、`DaVinci Resolve`、`AI agent`。
- 常见缩写保护，例如 `API`、`GPU`、`SRT`。
- 中英文之间的空格统一。
- 容易被错误拆行的术语标记。
- 标点和括号使用不一致。
- 口播不自然的超长句提示。

这让 CJK-English 能成为产品壁垒，但不把第一版拖进过重的排版工程。

### 10.3 富文本强调

MVP 支持：

- 加粗
- 斜体
- 下划线
- 颜色
- 说话人标签

用途：

- 强调重点
- 区分角色
- 提示口播强弱
- 多人脚本分配台词

### 10.4 Stage Cue 舞台提示

Stage Cue 是“怎么演”。

支持三种 MVP 形态：

```markdown
:stage[这句话要看镜头]{cue="look-camera" label="看镜头"}
```

```markdown
::stage[pause]{label="停顿" duration="1.5s"}
```

```markdown
:::stage{cue="demo-screen" label="切演示画面"}
打开产品后台首页。
鼠标停在「数据看板」区域。
:::
```

渲染原则：

```text
口播文本
        ↳ 舞台提示
```

Stage Cue 不应被当作口播文本参与语音跟随匹配，除非它绑定的正文部分本身是口播文本。

### 10.5 Cue Marker 场记标记

Cue Marker 是“这里是一个控制点”。

MVP 支持：

```markdown
::marker[M001]{type="retake" label="重录点" note="从这里开始重录"}
```

```markdown
::marker[M002]{type="section" label="第二部分开始"}
```

用途：

- retake
- 跳段
- 导演控制
- 后期定位
- 分段拍摄

Marker 应该进入导航和跳转系统，但不进入口播文本。

## 11. 语音实时转写与自动滚动

### 11.1 产品目标

不是做一个完整字幕工具，而是让提词器知道嘉宾说到哪里了。

### 11.2 工作流程

1. 控制端设置文稿和播放端。
2. 选择语音跟随模式。
3. 选择一个激活语音源。
4. 语音源实时转写嘉宾声音。
5. 系统把转写内容与口播文本做匹配。
6. 播放端根据匹配位置自动推进。
7. 播放端把当前位置和识别状态回传控制端。

### 11.3 匹配原则

语音匹配需要容错：

- 嘉宾可能漏词。
- 嘉宾可能换词。
- 嘉宾可能重复一句。
- 现场可能有噪音。
- Stage Cue 和 Marker 不参与口播匹配。
- 系统应优先在当前附近寻找匹配，避免突然跳到很远的位置。

### 11.4 控制端可见信息

控制端需要看到：

- 当前语音源
- 实时转写文本
- 当前匹配到的文稿位置
- 置信度
- 是否正在自动推进
- 是否需要人工接管

### 11.5 人工接管

语音跟随必须随时可被人工接管：

- 控制端暂停
- 控制端手动滚动
- 播放端手动滚动
- 跳转到 marker

人工操作后，系统应短暂停止自动跳动，再重新锁定当前位置附近的语音匹配。

## 14. 关键用户故事

### 14.1 本地扩展屏手动提词

作为控制者，我希望在主屏幕控制文稿滚动，并把扩展屏作为镜像播放端，这样嘉宾可以按我的节奏看词。

验收标准：

- 控制端和播放端可加入同一房间。
- 播放端可全屏镜像。
- 控制端预览区滚动时，播放端跟随。
- 控制端可随时暂停和恢复。

### 14.2 远程播放端自治

作为控制者，我希望远程播放端可以本地执行滚动，并把真实位置同步回来，这样远程网络不稳定时也不影响嘉宾阅读。

验收标准：

- 控制端下发文稿和配置。
- 播放端本地滚动。
- 播放端定期回传当前位置。
- 控制端显示播放端真实进度。
- 网络短暂中断时，播放端不清空画面。

### 14.3 录播改稿与版本回退

作为控制者，我希望每次关键改稿前后都能手动保存版本，这样录播现场说法改来改去时可以对比和回退。

验收标准：

- 控制端可保存当前稿件版本。
- 保存时可填写版本说明。
- 可查看版本列表。
- 可对比任意版本与当前草稿。
- 可把历史版本恢复成新的当前草稿。

### 14.4 语音跟随自动滚动

作为嘉宾，我希望提词器根据我实际说话节奏自动推进，而不是强迫我跟着固定速度念。

验收标准：

- 可选择一个激活语音源。
- 系统实时转写语音。
- 系统把转写结果匹配到口播文本。
- 播放端根据匹配位置推进。
- 控制端可看到转写结果、位置和置信度。
- 控制者可随时手动接管。

### 14.5 Stage Cue 与 Marker

作为控制者，我希望在文稿里插入舞台提示和场记标记，这样嘉宾知道怎么演，团队也能快速跳段和 retake。

验收标准：

- Stage Cue 显示为口播文本下方的提示。
- Cue Marker 显示为独立控制点。
- Marker 可以被控制端点击跳转。
- Stage Cue 和 Marker 不作为普通口播文本参与语音匹配。

## 15. 成功指标

### 15.1 北极星指标

**一次房间创建后，成功完成连续 10 分钟同步提词的比例。**

### 15.2 MVP 指标

- 从进入网站到开始播放的时间小于 60 秒。
- 本地扩展屏模式下，控制操作到播放显示的体感延迟小于 100ms。
- 远程模式下，播放端状态回传延迟可见且稳定。
- 断线重连后，播放端能恢复到当前房间状态。
- 现场改稿后，用户能在 10 秒内保存一个新版本。
- 用户能在 30 秒内找到并回退到一个历史版本。
- 语音跟随模式下，系统能稳定判断当前段落位置，而不是频繁大跳。

## 16. 风险与产品应对

| 风险 | 影响 | 产品应对 |
| --- | --- | --- |
| 远程滚动无法做到绝对实时 | 控制端拖动播放端时有延迟 | 不承诺远程像素级遥控，改为播放端自治和状态回传 |
| 语音识别不稳定 | 自动滚动跳错 | 只在当前附近匹配，显示置信度，支持人工接管 |
| 现场频繁改稿 | 文稿混乱，无法回退 | MVP 内置手动版本快照、对比、回退 |
| 多语言断行不佳 | 嘉宾阅读困难 | 编辑和播放渲染必须内置 CJK 与英文断行策略 |
| 舞台提示干扰口播 | 语音匹配和阅读混乱 | Stage Cue / Marker 与口播文本分层处理 |
| 多播放端状态不同 | 控制者不知道现场真实情况 | 每个播放端独立回传版本、进度和连接状态 |

## 17. 第一阶段产品结论

这个产品的核心不是“控制端远程操控播放端”，而是：

**控制端负责组织，播放端负责执行，房间负责同步事实。**

MVP 必须从第一天就支持：

1. 双视图房间。
2. 播放端本地滚动。
3. 控制端配置和文稿推送。
4. 播放端状态回传。
5. 稿件版本管理。
6. 语音转写驱动滚动。
7. Markdown 扩展文稿。

只要这七件事成立，它就不再是一个普通网页提词器，而是一个真正适合拍摄现场的在线提词系统。
